## 1. Settings Authentication Session [#settings-authentication-session]

The settings page is locked using the device's biometrics or credentials (if set).

Once unlocked, it will not prompt for login for the next 5 minutes.
This persisting session duration reset each time a settings page is accessed.

When the device is locked, or the app is exited or placed in the background,
the authentication session will be revoked.

## 2. Default Launcher [#default-launcher]

By setting {APP_NAME} as the default launcher (home screen) app, any attempts to
leave the app will simply re-open it.

To do this, use the `Launcher` option in [Setting Actions](/docs/setting-actions).

## 3. App Pinning / Lock Task Mode [#app-pinning-lock-task-mode]

### 3.1. User-owned Devices [#user-owned-devices]

On regular user-owned devices, to improve security, enable **Ask for
PIN/pattern/password before unpinning** in your device settings.

On some devices, it may be shown as **Lock device when unpinning** or equivalent.

This setting is accessible by first finding **App Pinning**, then clicking
into the item (instead of the toggle/switch) to see additional options.

This will ensure that users cannot unpin (and thus unlock) the kiosk view without
the device first locking itself and requiring your biometrics or credentials.

For more on Android App Pinning ([screen pinning](https://developer.android.com/about/versions/lollipop/android-5.0#ScreenPinning)), refer to:

1. [Google Official Documentation](https://support.google.com/android/answer/9455138)
1. [Samsung Guide for Unpin Lock](https://www.samsung.com/sg/support/mobile-devices/pin-an-app-to-your-phone-screen-so-that-it-cant-be-closed)

When in screen pinning mode, you will not be able to launch other applications.
See the ownership modes below for further details.

### 3.2. Device Policy Controller [#device-policy-controller]

If you have access to your
[Device Policy Controller (DPC)](https://developer.android.com/work/dpc/build-dpc),
or your MDM/EMM has provided an interface to do so, it is recommended that you
add {APP_NAME} to the allowlist of apps for lock task packages.

This has the benefits of:

1. removing warnings and instructions when you "lock" the app (as it is no
   longer
   [screen pinning](https://developer.android.com/about/versions/lollipop/android-5.0#ScreenPinning)
   like in user-owned devices)
1. stopping users from triggering the "unpin" action using gestures or holding
   the back and overview button, thus removing the side-effect of the device
   getting locked when users attempt to "unpin"

In
[Lock Task Mode](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode),
the in-app unlock methods are configurable and can be disabled. An eligible
DPC can also end Lock Task by updating its policy. The in-app methods are:

1. Opening the Kiosk Control Panel by either
   - holding the back button
   - tapping the screen 10 times in quick succession at your configured region
     (e.g. Top Left quadrant)
1. Adding a custom unlock shortcut (requires a physical keyboard or
   a method of that sending key combinations, e.g. `CTRL+1`)

There are also standalone applications that, when granted eligible ownership, can
perform the duties of a DPC. Below are instructions for two popular applications:
1. Google's [Test DPC](https://github.com/googlesamples/android-testdpc)

   - Go to `Lock Task -> Manage lock task list` and enable {APP_NAME}.

2. [OwnDroid](https://github.com/BinTianqi/OwnDroid)

   - Go to `System -> Lock Task Mode -> Applications` and add {APP_NAME}'s package
   name, which you can find in the [Settings -> About](/docs/settings/about) screen.

Finally, if you are writing your own DPC, the kotlin code to achieve this would be:

```kt
val APP_PACKAGES = arrayOf(
  // Choose one depending on your installation method:
  "uk.nktnet.webviewkiosk",   // GitHub, F-Droid, IzzyOnDroid, etc
  "com.nktnet.webview_kiosk", // Aurora Store, Google Play Store
)

val dpm = context.getSystemService(Context.DEVICE_POLICY_SERVICE) as DevicePolicyManager
val adminName = getComponentName(context)
// Android 8+ (API 26+): preserve packages already allowed by the DPC.
val packages = (dpm.getLockTaskPackages(adminName).toList() + APP_PACKAGES).distinct()
dpm.setLockTaskPackages(adminName, packages.toTypedArray())
```

For more information, see
[Android's official documentation](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode#allowlist_apps).

### 3.3. Device Owner Mode [#device-owner-mode]

When set as the device owner, {APP_NAME} can act as a DPC and automatically adds itself to the
[allowlist for lock task packages](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode).
It is also possible for {APP_NAME} to add other applications in settings, thus allowing it to
launch other apps in Lock Task Mode (kiosk).

The easiest way is to factory reset your device and use the
[QR Code installation method](/docs/installation#qr-code-provisioning).

However, if this isn't possible, you can try the following:

<Step>

### 3.4. Main-user Profile Owner [#profile-owner-mode]

A Profile Owner can manage an existing **full Android user**, including the main
user, without creating a work profile. This is different from a Profile Owner
inside a separate managed work profile. Device Owner is still the recommended
mode for a fully managed dedicated kiosk.

Android 9 (API 28) and later allow a full-user Profile Owner to configure Lock
Task packages and features when **no Device Owner is set**. Android 8 (API 26)
and later also support affiliated secondary users managed alongside a Device
Owner. Android enforces affiliation and clears Lock Task policy when a user
becomes unaffiliated. An ordinary unaffiliated work-profile owner cannot use
these policies. Do not grant affiliation just to bypass an organisation's policy.

{APP_NAME} checks the actual owner and queries Lock Task policy access before
exposing its controls. A successful read is not a guarantee that a later write
will succeed: permission can be revoked, and policies can conflict. Failed writes
are handled without replacing an unreadable allowlist. Existing package entries,
including packages not installed or shown in the app list, are preserved when
adding or removing an app.

#### ADB setup [#profile-owner-adb]

1. Install {APP_NAME} in the intended full user. Enable USB debugging and connect
   a computer with [ADB](https://developer.android.com/tools/adb).
2. Find the foreground full user and inspect the device's users:

   ```sh
   adb shell am get-current-user
   adb shell pm list users
   ```

3. Substitute that ID for `USER_ID` below. Do not select a managed work-profile
   ID. The main user is often 0, but it need not be, particularly on devices with
   a headless system user. App detection uses Android APIs, never an ID-0 test.

   ```sh
   adb shell dpm set-profile-owner --user USER_ID uk.nktnet.webviewkiosk/.WebviewKioskAdminReceiver
   ```

   Google Play/Aurora installations use a different package and need the full
   receiver class name:

   ```sh
   adb shell dpm set-profile-owner --user USER_ID com.nktnet.webview_kiosk/uk.nktnet.webviewkiosk.WebviewKioskAdminReceiver
   ```

4. Open the app in that user. Check **Settings → Device → Manage Device Policies**
   and **Settings → About**. Confirm Profile Owner, Full Android user, and Lock
   Task policy capability. The `get_system_info` response field
   `data.app.lockState` reports `LOCK_TASK` for genuine kiosk mode and `SCREEN_PINNING` for the
   user-exitable mode. Being allowlisted alone does not mean Lock Task is
   currently running.

The [installation tool](/tools/qr-installation) can generate these commands for
the chosen user and installation source. Account, existing-owner, and completed
setup restrictions vary by Android release and OEM. Use an eligible, account-free
test device; follow the exact `dpm` error instead of bypassing ownership checks.
Do not remove an organisation's existing management configuration to enroll.

#### Why main-user Profile Owner setup uses ADB [#profile-owner-qr]

Android supports **Profile Owner enrollment through QR for a separate work
profile** on compatible devices and Android versions. It does not expose a
standard QR enrollment mode that assigns a Profile Owner to the existing main
user. Google's provisioning guide uses "Profile Owner" for work-profile
enrollment; it does not mean full-user Profile Owner enrollment.

The setup wizard owns the provisioning flow. On Android 12+, it supplies the
allowed modes to the DPC, which must return one of those modes:

| Android provisioning mode | Result |
| --- | --- |
| `PROVISIONING_MODE_FULLY_MANAGED_DEVICE` | Device Owner on a fully managed device |
| `PROVISIONING_MODE_MANAGED_PROFILE` | Profile Owner in a separate managed work profile |
| `PROVISIONING_MODE_MANAGED_PROFILE_ON_PERSONAL_DEVICE` | Profile Owner in a separate work profile on a personal device, when offered by the initiator |

None is an "existing main-user Profile Owner" mode. Adding a custom mode or user
ID to a QR payload or its admin extras does not grant the app authority to
change Android's owner-assignment rules. Switching to a work-profile mode would
create a different user scope, with different kiosk restrictions.

The ADB `dpm set-profile-owner --user USER_ID` command is a privileged shell setup
path that directly requests assignment for the selected existing user, subject
to Android's account and ownership checks. The tool therefore offers ADB for
main-user Profile Owner setup and QR for Device Owner setup. Its work-profile
option explains the separate enrollment flow; it does not generate a main-user
Profile Owner QR code. Webview Kiosk's provisioning activity continues to request
fully managed enrollment and rejects a work-profile-only list of allowed modes.

References:

- [Google's provisioning modes and version matrix](https://developers.google.com/android/work/play/emm-api/prov-devices)
- [Allowed provisioning mode selection](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#ACTION_GET_PROVISIONING_MODE)
- [Android provisioning mode constants](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#PROVISIONING_MODE_MANAGED_PROFILE)

#### Capabilities and limits [#owner-capabilities]

| Operation | Device Owner | Eligible full-user Profile Owner | Ordinary work-profile Profile Owner |
| --- | --- | --- | --- |
| Configure Lock Task packages | Yes | Android 9+ without a Device Owner; Android 8+ for affiliated secondary users | Unavailable unless Android explicitly grants eligible affiliation/policy access |
| Configure Lock Task features | Android 9+ | Android 9+ when policy access is granted | Unavailable for ordinary unaffiliated work profiles |
| Start genuine Lock Task | App must be allowlisted | App must be allowlisted | Ownership alone is insufficient; check Android's allowlisting result |
| Lock the whole device (`lock_device`) | Requires declared force-lock policy | Requires full-user scope and force-lock policy | Not exposed as a whole-device command by this app |
| Transfer native ownership | Android 9+ | Android 9+, retaining Profile Owner scope | Android 9+, retaining work-profile scope |
| Remove native owner in app | Testing only; best-effort cleanup | Android 7+ on full users (`clearProfileOwner`); testing only | Not offered; clearing a work-profile owner is not supported by that API |

Profile Owner does not gain all Device Owner powers, manage other users, or
become a fully managed device. Only permissions for each operation are used.
Dhizuku does not enable native-only ownership removal or transfer in this app.
The `lock_device` capability also checks the
actual owner's declared force-lock policy. Work-profile `lockNow()` behaviour
can depend on whether a separate work challenge is enabled, so this app does
not expose it as a device-wide command.

Android's clear-owner APIs are deprecated and intended for testing. Cleanup is
best-effort: some policies and user data can remain after ownership is removed.
The in-app confirmation explains this limitation. Use your organisation's reset
or unenrollment process for production devices; the app does not automatically
wipe a main user to remove ownership. See
[clearProfileOwner](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#clearProfileOwner(android.content.ComponentName)).

On Android 11+, user scope comes from `UserManager.isManagedProfile()`; on
Android 13+, `isProfile()` also identifies other profile types. On Android 7–10,
a Profile Owner can use `DevicePolicyManager.isManagedProfile(admin)`. On older
versions, a known Device Owner or Android's system-user check can identify a
full user; otherwise the UI reports Unknown rather than guessing. Independent
Profile Owner Lock Task support is not assumed on those old releases.

On Android 5–7.1, the Lock Task package getter exists in AOSP but was not yet a
public SDK API. For legacy Device Owners the app attempts this getter only on
those releases, before non-SDK enforcement, so it can merge existing entries.
If the OEM does not supply it, the app leaves the policy untouched. Android 8+
uses the public getter. The advanced Block Activity Start in Task feature requires
Android 11+.

#### Dhizuku shared ownership [#dhizuku-profile-owner]

Install [Dhizuku](https://github.com/iamr0s/Dhizuku) in the **same full Android
user** as {APP_NAME}, then assign it the desired owner role. For Profile Owner:

```sh
adb shell dpm set-profile-owner --user USER_ID com.rosan.dhizuku/.server.DhizukuDAReceiver
```

Open {APP_NAME}, go to **Device → Manage Device Policies**, and grant Dhizuku
permission. The status distinguishes **Dhizuku: Profile Owner** from
**Dhizuku: Device Owner** and shows the user scope. Android 9+ is required for
this app's Dhizuku integration. Permission granted to the personal-user app does
not automatically grant it to the work-profile copy.

Shared permission grants the capabilities of Dhizuku's actual owner role in
that user. Sharing ordinary work-profile ownership does not promote it to
full-user or Device Owner authority. A denied, revoked, unavailable, or dead
Dhizuku connection disables management operations; existing external allowlisting
can still permit Lock Task.

#### External DPC and lock state [#external-dpc-lock-state]

An eligible external DPC can allowlist {APP_NAME} without granting it ownership or
Dhizuku access. The app honours `isLockTaskPermitted()` and leaves the external
DPC's policy intact. External policy controls are unavailable in the app; the
local Home-button preference does not override an external DPC's app allowlist.

On Android 6+, actual runtime state is reported separately as `NONE`, `LOCK_TASK`,
`SCREEN_PINNING`, or `UNKNOWN`. Android 5–5.1 cannot distinguish pinning from
Lock Task using the public state API, so the detailed state is Unknown. Screen
pinning remains available when Android does not allowlist the app; it is never
reported as genuine Lock Task merely because an owner exists.

## 4. Managed Configurations (App Restrictions) [#managed-configurations-app-restrictions]

With an eligible Device Owner or Profile Owner in the same user, you can use
[managed configurations](https://developer.android.com/work/managed-configurations)
to restrict and remotely modify {APP_NAME} settings through your MDM/EMM.

It is also possible to set app restrictions using [OwnDroid](https://github.com/BinTianqi/OwnDroid)
or [Test DPC](https://github.com/googlesamples/android-testdpc).

For a list of available settings, refer to
[./app/src/main/res/xml/app_restrictions.xml](https://github.com/nktnet1/webview-kiosk/blob/main/app/src/main/res/xml/app_restrictions.xml).

Below are instructions for a few popular MDM/EMM providers:

- [Google Endpoint Management](https://support.google.com/a/answer/6328701?hl=en#configure&zippy=%2Cset-up-android-apps-with-managed-configurations)
- [Microsoft Intune](https://learn.microsoft.com/en-us/intune/intune-service/apps/app-configuration-policies-managed-app)
- [Miradore](https://www.miradore.com/knowledge/android/how-to-configure-application-settings)
- [Manage Engine](https://www.manageengine.com/mobile-device-management/managed-app-configuration.html)
- [Scale Fusion](https://help.scalefusion.com/v1/docs/application-configurations-for-android-applications)
- [Hexnode](https://www.hexnode.com/mobile-device-management/help/set-up-permissions-and-configurations-for-an-app-using-hexnode-mdm)

At the time of writing, [Headwind MDM](https://h-mdm.com) (an open-source
platform to manage android device) does not yet support managed configurations,
but this is [on their roadmap for the future](https://github.com/h-mdm/hmdm-server/issues/49#issuecomment-3574073134).
