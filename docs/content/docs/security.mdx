For ownership setup, choose a method in [Device Activation](/docs/activation).

## 1. Settings Authentication Session [#settings-authentication-session]

Settings use the device's biometrics or screen-lock credentials when configured.
A successful login keeps settings unlocked for five minutes. Visiting a settings
page renews that session.

Locking the device, leaving the app, or putting it in the background ends the
session. Configure a device screen lock and the app's unlock methods before
using it as a kiosk.

## 2. Default Launcher [#default-launcher]

Setting {APP_NAME} as the default launcher brings users back to the kiosk when
they press Home. Launcher selection alone does not prevent access to other apps
or Android settings. Use it together with the appropriate locking mode.

The launcher option is in [Setting Actions](/docs/setting-actions).

## 3. App Pinning and Lock Task Mode [#app-pinning-lock-task-mode]

### 3.1. Personal devices [#user-owned-devices]

For screen pinning, enable **Ask for PIN/pattern/password before unpinning**
in Android Settings. Some devices call this **Lock device when unpinning**.
Without it, users can unpin the app without authenticating.

Screen pinning is Android's user-controlled fallback. Other apps cannot be
launched while the kiosk is screen-pinned.

### 3.2. Managed devices [#device-policy-controller]

Lock Task Mode prevents the normal unpin gesture. The app must be allowed by
an eligible Device Policy Controller (DPC), which may be {APP_NAME}, Dhizuku,
or your organisation's management app.

Configure in-app unlock methods carefully. The Kiosk Control Panel can be
opened using the configured back-button hold, screen taps, or keyboard shortcut.
An eligible external DPC can also end Lock Task by changing its policy.

### 3.3. Device Owner [#device-owner-mode]

Device Owner gives an app broad control over the device. {APP_NAME} can manage
its Lock Task allowlist and supported kiosk features when granted this role.
Only one Device Owner can be configured.

### 3.4. Profile Owner [#profile-owner-mode]

Profile Owner controls its Android user or profile. An eligible Profile Owner
in the main full user can manage kiosk policies while retaining a separate work
profile where Android allows it. A work-profile owner does not automatically
have authority over the whole device or the personal copy of the app.

### 3.5. Capabilities and limits [#owner-capabilities]

| Operation | Device Owner | Eligible full-user Profile Owner | Ordinary work-profile Profile Owner |
| --- | --- | --- | --- |
| Choose Lock Task apps | Yes | Depends on Android version and policy authority | Requires eligible affiliation/policy access |
| Configure Lock Task features | Android 9+ | Android 9+ with policy access | Unavailable in ordinary unaffiliated work profiles |
| Lock Task Mode | App must be allowlisted | App must be allowlisted | Ownership alone is insufficient |
| Transfer native ownership | Android 9+ | Android 9+, retaining owner scope | Android 9+, retaining profile scope |
| Deactivate owner | Testing only | Android 7+ on full users, testing only | Not offered |

The Device Policies status card shows the actual owner role, native or shared
source, user scope, and available policies. Unavailable controls explain the
missing permission or version requirement. **Restricted** means an app setting
has been managed by an administrator.

### 3.6. Shared ownership [#dhizuku-profile-owner]

Dhizuku shares its existing owner's authority; it does not create a second
Device Owner. Revoking permission or stopping Dhizuku removes access to its
shared policies. Native owner removal and transfer are not available through
this connection. See [Dhizuku setup](/docs/activation/dhizuku).

### 3.7. External management and lock state [#external-dpc-lock-state]

An external DPC can allowlist {APP_NAME} without sharing its ownership. That
DPC retains control of the policy. See [External DPC setup](/docs/activation/external-dpc).

Allowlisting does not mean Lock Task is currently running. Remote
`get_system_info` reports `data.app.lockState` as `LOCK_TASK`, `SCREEN_PINNING`,
`NONE`, or `UNKNOWN`. Android 5–5.1 reports Unknown because it cannot distinguish
pinning from Lock Task.

See [Android's Lock Task guide](https://developer.android.com/work/dpc/dedicated-devices/lock-task-mode).

## 4. Managed Configurations [#managed-configurations-app-restrictions]

An eligible owner in the same user can restrict and remotely change app
settings using [managed configurations](https://developer.android.com/work/managed-configurations).
Local settings marked **Restricted** cannot be overridden in the app.

See the [available restrictions](https://github.com/nktnet1/webview-kiosk/blob/main/app/src/main/res/xml/app_restrictions.xml)
and your MDM provider's guidance, such as [Google Endpoint Management](https://support.google.com/a/answer/6328701),
[Microsoft Intune](https://learn.microsoft.com/en-us/intune/intune-service/apps/app-configuration-policies-managed-app),
or [Hexnode](https://www.hexnode.com/mobile-device-management/help/set-up-permissions-and-configurations-for-an-app-using-hexnode-mdm).

Owner removal is intended for testing and may leave policies or user data
behind. For production unenrollment, use your organisation's managed reset
process.
